Final Decision — Mastodon Fridge Backend MVP

This document closes the loop across backend-high-level-plan.html, backend-plan-review.html, and 2nd-assess-backend-plan.html. Every contested point now has a single, binding answer. Goal: a 50-user closed beta that ships in ~2.5–3.5 weeks of focused work and is safe enough to put real students in front of.

Final pass Date: 2026-05-08 Target: ~50 PFW users Stack: Expo + Supabase

Bottom Line

The second assessment is correct on every substantive disagreement with my original review. The Microsoft 365 / Outlook fact about PFW email is the one that matters most — that part of my review was an unverified assumption and the second assessment was right to push back. The storage cap math and the "add friends and notifications now" overscope were also fair corrections.

With those concessions made, the second assessment is ~90% ready to execute. The remaining 10% is in choices it left intentionally soft ("maybe", "benchmark first", "auto-approve if too slow") that a ship-fast MVP needs to commit to. This document picks one option in each of those places and stops debating.

Verdict: Adopt the second assessment as the working plan with the seven concrete commitments below. After that, no more planning rounds — start building Phase 0.

Concessions to the Second Assessment

Where the second assessment overrides my original review.

Concede — factual error

PFW students do not have Google Workspace accounts

PFW student email runs on Microsoft 365 / Outlook. The hd=pfw.edu proposal in the original review assumed a Google Workspace tenant that does not exist. Drop it entirely. Auth direction stays Google sign-in for general identity + optional @pfw.edu email OTP for the verified badge, exactly as the original plan and the second assessment describe.

Concede — wrong number

15 GB global storage cap is not free-tier compatible

Supabase free tier includes 1 GB of file storage. The 15 GB figure assumed Pro. Replace with a free-tier-compatible cap and an explicit upgrade trigger.

Concede — overscope

friendships, notifications, and event_attendance were premature

The Friends tab is a placeholder. There is no notification feature. The UI does not currently distinguish "pinned to fridge" from "RSVP'd." Adding tables ahead of features is exactly what the second assessment rightly called out. Defer all three; add when the screens require them.

Concede — overengineering

Soft delete on every table is too much for a 50-user MVP

deleted_at on every table forces every query to add WHERE deleted_at IS NULL and complicates RLS. Limit soft delete to events and gallery_media (where audit/dispute matters). Hard delete is fine for fridge_items, media_stickers, and media_reports.

Seven Commitments That Close the Remaining Open Questions

The second assessment left these intentionally soft. Shipping fast means picking one and moving on.

Decision 1 — Moderation default

Closed beta uploads default to approved, not pending

The schema supports pending | approved | rejected | removed. For the 50-user invited cohort, default new uploads to approved — these are people you trust by invitation. Reports flag content; an admin can mark removed. When the app opens beyond the invited cohort, flip the default to pending in one migration. This avoids shipping a moderation queue with no human to drain it.

Decision 2 — AI model starting point

Phase 5 starts with Claude Haiku 4.5; escalate to Sonnet 4.6 only if accuracy fails

Pick a default and benchmark in flight. Haiku 4.5 (claude-haiku-4-5-20251001) is the cheapest vision-capable Claude model and is the right baseline. After the first 20–30 real PFW flyers, if title / date / location extraction is below ~85% field accuracy, swap to Sonnet 4.6 (claude-sonnet-4-6) without changing the Edge Function shape.

Decision 3 — Dev auth mechanics

Real Supabase Auth users with email/password, auto-login gated on __DEV__

Create two Auth users: dev1@local.test and dev2@local.test. Credentials live in a local .env.local as EXPO_PUBLIC_DEV_AUTH_EMAIL / EXPO_PUBLIC_DEV_AUTH_PASSWORD. The client only auto-logs-in when __DEV__ === true and the env vars are present. Production builds (no env vars injected) cannot dev-auth even by accident. RLS stays on the entire time.

Decision 4 — Realtime

No realtime subscriptions in MVP

Pull-to-refresh on the gallery, refetch on tab focus. The Supabase Realtime client adds complexity (channel lifecycle, reconnection) that is not justified for 50 users. Revisit only if "photos appearing as friends upload" becomes a hero moment in user testing.

Decision 5 — Storage tier and caps

Free tier with image-only uploads; storage alarm at 750 MB; upgrade trigger at 850 MB

Per-user: 100 MB total, 5 MB per image, 30 photos per event per user. Per-event: 500 MB total. Global alarm at 750 MB used (~75% of free tier). At 850 MB used, upgrade to Supabase Pro and lift per-user caps. Video disabled for MVP entirely — if a user picks a video, the client rejects it before upload. Compress client-side via expo-image-manipulator at ~1600px longest edge / JPEG q70.

Decision 6 — Storage buckets and access mode

All buckets private; reads through signed URLs from the server

Three buckets: flyers, gallery, avatars, all private. The client requests a signed read URL via a tiny RPC / Edge Function that verifies the requesting user is authenticated and (for gallery media) that the linked row's moderation_status is not removed. More conservative than the second assessment's "public reads after moderation"; same operational cost; far fewer ways to leak content. Path convention: {bucket}/{user_id}/{uuid}.{ext}, gallery uses gallery/{event_id}/{user_id}/{uuid}.{ext}.

Decision 7 — Migrations and env hygiene

Plain supabase/migrations folder, applied via supabase db push; no CI yet

Every schema change is a numbered SQL file in supabase/migrations. Apply via the Supabase CLI; no migration framework, no GitHub Actions yet. Two Supabase projects: dev (free tier, throwaway) and prod (created at Phase 6, before real users). Env files: .env.local for dev, .env.production committed never. .env.local in .gitignore.

Final Phase Plan

Eight phases from the original plan compressed into seven, with concrete time estimates for one focused developer.

0

Foundation ~2 days

  • Create dev Supabase project and the two dev Auth users.
  • Write the first migration: schema, RLS policies, indexes — all in one file.
  • Wire the Expo client: anon key, dev auto-login, basic data layer.
  • Scaffold one Edge Function (extract-flyer) with the Anthropic key set; return a stub.
  • Verify cross-user isolation by attempting a forbidden read from dev2 against dev1's fridge_items.
1

Events & Market ~3 days

  • Manual event create / list / detail backed by Supabase.
  • ILIKE search on title + description; no pg_trgm, no FTS.
  • RLS: any authenticated user reads non-deleted events; only created_by can update.
2

Fridge customization ~2 days

  • Persist fridge_items with debounced writes (1.5s, plus on screen exit and app background).
  • Hold edits in memory + AsyncStorage; flush via batched upsert.
  • RLS: owner-only read and write on fridge_items.
3

Storage + media safety skeleton ~2 days

  • Create the three private buckets and storage RLS policies.
  • Client-side image compression before upload; reject anything over 5 MB.
  • Add the signed-URL RPC (get_signed_media_url(media_id)) that checks auth + moderation status and returns a short-lived URL.
4

Public galleries with reports ~3 days

  • Upload to gallery_media with moderation_status='approved' default.
  • Gallery feed pulls signed URLs through the RPC.
  • Tap-to-report writes media_reports; admin marks removed via a tiny admin-only screen or SQL.
  • Sticker overlays as separate media_stickers rows.
5

AI flyer extraction ~3 days

  • Edge Function calls Claude Haiku 4.5 with the flyer image; returns a strict JSON schema.
  • Client validates against the schema; ConfirmScreen always allows manual correction.
  • Per-user rate limit: 20 extractions per day, enforced server-side.
  • After the first 20–30 real flyers, evaluate accuracy; swap to Sonnet 4.6 if needed.
6

Production auth + prod project ~3 days

  • Create the prod Supabase project and run all migrations.
  • Replace dev auto-login with Google sign-in via Supabase Auth.
  • Optional @pfw.edu magic-link verification through a transactional email provider (Resend or Postmark — pick one in this phase).
  • Verified state stored in profiles.pfw_verified_at as a badge, not a gate.
7

Ship gate ~1 day

  • RLS audit: a script that signs in as dev2 and tries forbidden reads/writes against dev1's rows. Must fail every one.
  • Storage usage check: under 750 MB on dev, under 200 MB on prod at zero users.
  • Update CLAUDE.md and AGENTS.md: Firebase removed, Supabase added.
  • Confirm Supabase backup posture (free tier limits documented; Pro upgrade trigger noted).

Total: ~19 working days ≈ 2.5–3.5 weeks for one focused developer including normal slippage.

Ship Gate — MVP "done" checklist

  • All 9 existing screens load against real Supabase data, not mocks.
  • End-to-end flow works: create event → pin to fridge → upload gallery photo → scan flyer → confirm.
  • Two test users see the same events and the same approved gallery, but only their own fridge.
  • Reports flow works end-to-end: report → admin removes → photo no longer returned by signed URL.
  • RLS audit script passes (dev2 cannot read or write dev1's owned data).
  • Total prod storage under 200 MB at zero real users; alarm wired at 750 MB.
  • No service-role key, Anthropic key, or OAuth secret reachable from the Expo bundle.
  • CLAUDE.md and AGENTS.md reflect Supabase as the chosen backend.

Things this document deliberately does NOT include

Account deletion / GDPR endpoint

Not in MVP scope. Manual deletion via admin SQL is sufficient for a 50-user invited cohort. Add a real "delete my account" path before the app opens beyond the cohort.

Moderation queue UI

Closed-beta default of approved means there is no queue to drain. Reports flow into a simple list; admin acts via SQL or a one-screen tool. Build a real moderator UI when the default flips to pending.

Push notifications

No notification feature ships. Adding Expo Notifications, FCM, and APNs config before there is a trigger is exactly the overscope this plan is avoiding.

Observability beyond Supabase logs

Sentry / PostHog / similar is deferred until after the ship gate. Supabase function logs and Postgres logs are sufficient for diagnosing 50-user-scale issues.
