Mastodon Fridge Backend High-Level Implementation Plan

A pragmatic backend roadmap for a 50-user MVP: prioritize fast Expo Go/web testing, simple operations, future-safe data modeling, and delayed production authentication hardening.

Audience: senior developer review Scope: backend planning only Target: ~50 initial users Source: current product discussion

Executive Summary

Recommended Backend Direction

Use Supabase as the primary backend platform for the MVP: Postgres database, Auth, Storage, Row Level Security, and Edge Functions where server-side code is needed.

Authentication Strategy

Delay login enforcement during active frontend/backend testing, but model all user-owned data with future auth fields from the beginning.

Testing Strategy

Use a temporary development identity so Expo Go and web testing are not blocked by repeated sign-ins. Replace the dev identity with real Supabase Auth later.

Primary MVP Features

Events, Market discovery, customizable personal fridge layout, flyer/media storage, public event galleries, and a later AI extraction integration.

Core principle: Delay authentication in the user experience, not in the data model. This allows fast iteration now without requiring a database redesign later.

Confirmed Product Assumptions

Scale
Initial target is approximately 50 users, not a campus-wide launch.
Backend Platform
Prefer Supabase for lower operational overhead and faster MVP delivery.
Initial Auth UX
No required login during early testing. Use a temporary development user identity.
Production Auth Direction
Google sign-in first, followed by optional PFW student verification.
PFW Verification
Optional later verification via a code or magic link sent to an @pfw.edu Outlook inbox.
Galleries
Event galleries are public to all signed-in users for the MVP.
Deployment
Undecided. Supabase hosted services should cover the initial backend needs.

Recommended Architecture

Client

  • Expo React Native app
  • Expo Go and web testing support
  • Temporary dev identity provider
  • Later Supabase Auth session provider

Supabase

  • Postgres for relational data
  • Storage for flyers and gallery media
  • Auth for Google sign-in
  • RLS policies before production use

Server-Side Functions

  • AI extraction endpoint
  • Optional media moderation
  • Privileged storage operations
  • Future notification jobs
Recommended default: avoid a separate Express/Fastify backend for the first 50-user MVP unless a feature clearly requires long-running custom server logic. Supabase reduces infrastructure surface area.

Authentication Assessment

Option Pros Cons Recommendation
Google sign-in only Simple, familiar, quick to implement, low friction. Does not prove PFW affiliation. Use for production login baseline.
PFW email OTP only Campus-scoped without official school SSO. More friction; still only proves mailbox access, not active enrollment. Do not use as the first required login path.
Google + optional PFW verification Good usability now, campus verification later. Two-step model adds product complexity. Best fit for current MVP direction.
Official Microsoft/PFW SSO Strongest institutional trust model. Likely requires school approval, Azure configuration, and Duo/tenant constraints. Defer until official partnership is realistic.
Security limitation: optional PFW verification proves access to an @pfw.edu mailbox, not official enrollment. Stronger identity requires official university SSO or manual approval.

High-Level Data Model

Table Purpose Important Fields
profiles App-specific user profile connected to future Supabase Auth user. id, display_name, avatar_url, pfw_email, pfw_verified_at
events Campus events visible in Market and attachable to fridges. id, title, starts_at, ends_at, location, flyer_image_path, created_by
fridge_items User-specific pins, stickers, notes, and layout state on the personal fridge. id, user_id, event_id, x, y, rotation, scale, z_index, sticker_type
gallery_media Public event photos/videos uploaded by users. id, event_id, uploaded_by, media_path, media_type, moderation_status
media_stickers Sticker/reaction overlays placed on gallery media. id, media_id, placed_by, sticker_type, x_percent, y_percent
Key modeling decision: even before real auth is enabled, user-owned records should include user_id or created_by. During development, those fields point to a seeded dev user.

Implementation Phases

0

Backend Foundation and Decisions

  • Create Supabase project and environment configuration.
  • Define schema migrations for profiles, events, fridge items, gallery media, and media stickers.
  • Create one seeded development user for auth-free testing.
  • Document which features are dev-only and not production secure yet.
1

Events and Market Discovery

  • Build event creation, event listing, event detail, and search/filter support.
  • Use public read access for signed-in users later; use dev-mode access during testing.
  • Keep Market independent from AI extraction so manual events work first.
2

Personal Fridge Customization

  • Persist per-user fridge items and layout metadata.
  • Support drag position, rotation, scale, z-order, sticker choice, and optional note text.
  • Treat customization as a cross-functional feature: frontend gestures plus backend persistence.
3

Storage for Flyers and Gallery Media

  • Create storage buckets for flyers, gallery media, and avatars if needed.
  • Compress images before upload and store only paths/metadata in Postgres.
  • Add file size and media type limits appropriate for a 50-user MVP.
4

Public Event Galleries

  • Allow users to upload media to event galleries.
  • Allow all signed-in users to view event gallery media.
  • Store sticker overlays separately from the original media asset.
5

AI Flyer Extraction

  • First stabilize manual event creation and confirmation UI.
  • Add an AI extraction function that returns structured event fields.
  • Validate AI output before saving and always allow manual correction.
  • Add scan rate limits before broad testing to control cost.
6

Google Auth Integration

  • Replace the temporary dev identity with Supabase Auth user sessions.
  • Backfill or migrate dev data if needed.
  • Ensure fridge items, uploads, and profile records use the authenticated user ID.
7

Optional PFW Verification

  • Add an optional prompt: “Verify as a PFW student?”
  • Send verification link or code to an @pfw.edu email address.
  • Store verification status on the profile without making it required for basic use.
8

Security and Production Hardening

  • Enable and test Row Level Security policies.
  • Restrict writes to authenticated owners where appropriate.
  • Add moderation status for public gallery uploads.
  • Add basic audit logging, error tracking, and backup review.

Definition of Done Per Backend Phase

  • Database schema is migrated through a repeatable migration path.
  • Data ownership fields are present even if real auth is not enabled yet.
  • Expo Go and web can test the feature without repeated login during early development.
  • Every write path validates required fields and rejects invalid data.
  • Every public surface has a clear privacy assumption documented.
  • Senior developers can review table design, storage policy, and security gaps before production use.

Open Questions for Senior Review

  1. Should Supabase direct client access be used for most CRUD, or should critical writes go through Edge Functions?
  2. What is the minimum acceptable Row Level Security policy set before beta testing with real users?
  3. Should gallery media uploads require moderation before becoming visible, or can moderation be added after private beta?
  4. Should PFW verification ever gate write access, or remain a profile badge/trust signal?
  5. What storage limits should be enforced per user, per event, and globally for the MVP?

This document intentionally replaces prior backend planning assumptions for review purposes and reflects the current MVP direction.
