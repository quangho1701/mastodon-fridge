Second Assessment of the Backend Plan Review

This document evaluates backend-plan-review.html against the current Mastodon Fridge MVP goal: a fast-moving, low-maintenance backend for roughly 50 initial users, while avoiding decisions that make real authentication, media safety, or Supabase security painful later.

Prepared: 2026-05-08 Input: backend-high-level-plan.html Input: backend-plan-review.html Output: recommended backend direction

Bottom Line

The senior review is mostly technically sound. The strongest points are about Supabase Row Level Security, avoiding a fake unauthenticated dev user, moving moderation structure earlier, defining storage policies, and documenting the Firebase-to-Supabase pivot. Those are not overthinking; they are cheap changes now and expensive changes later.

The review does overreach in a few places. It assumes PFW likely has Google Workspace accounts, but the available PFW/Purdue documentation points toward Microsoft 365/Outlook for student email. It also pulls in friends, attendance, and notifications earlier than the MVP probably needs. For a 50-user MVP, we should add safety and ownership primitives now, but avoid building a social graph or notification system before the product proves it needs them.

Recommended outcome: revise the backend plan, but do not dramatically expand scope. Adopt the security foundations, moderation skeleton, storage conventions, and docs cleanup. Defer friends, notifications, and official PFW/Google-domain assumptions.

Verdict Summary

Adopt Directly

  • Use Supabase for the MVP instead of a custom backend service.
  • Enable RLS from the first migration, not at the end.
  • Use real Supabase Auth dev users instead of unauthenticated fake ownership.
  • Keep service-role keys and AI keys out of the Expo bundle.
  • Add timestamps, indexes, storage conventions, and media reports early.

Adopt With Changes

  • Moderation should exist early, but it can be lightweight and manual for the closed beta.
  • Gallery storage should start private or signed-url based unless you intentionally accept public URLs.
  • AI model choice should be benchmarked on real flyers, not locked by assumption.
  • Storage caps should match the actual Supabase tier being used.
  • PFW verification should remain optional and mailbox-based unless official SSO happens.

Defer

  • friendships table until the Friends tab becomes real.
  • notifications table until notifications have a concrete MVP use case.
  • Realtime gallery updates until basic gallery upload/view flows are stable.
  • Video upload unless you are ready for storage and moderation complexity.
  • Official Microsoft/PFW SSO until school approval exists.

Reject / Treat As Unproven

  • Do not assume PFW students have Google Workspace accounts on pfw.edu.
  • Do not collapse optional PFW verification into Google hd without proof.
  • Do not set storage caps that exceed the selected Supabase plan.
  • Do not make every possible future social feature a Phase 0 table.

Detailed Assessment of Senior Review Claims

Review Claim Assessment Recommended Action
Adopt Seeded dev user is underspecified. Correct. A plain seeded UUID does not exercise Supabase Auth or RLS. It creates a security cliff later. Service-role keys must never be in the client, and RLS-off development gives false confidence. Use 2–3 real Supabase Auth dev users in a dev project. Auto-login for development builds only. Keep RLS on and test owner-isolation from day one.
Adopt RLS should be enabled at table creation. Correct. Supabase exposes client-side database access through the anon/publishable key, so RLS is the core safety boundary if the app talks directly to Supabase. Every migration should include RLS policies. Start simple: authenticated read for public tables, owner-only write for user-owned tables, no anonymous production access.
Modify Gallery moderation cannot wait until hardening. Correct in principle. However, for a 50-user closed beta, we do not need ML moderation or a large admin system immediately. We do need the database fields and a manual removal/report path. Add moderation_status, media_reports, trusted-user flags, and owner/admin removal. Disable video at first. Auto-approve trusted beta uploads if manual pre-approval is too slow.
Modify Missing tables: friends, attendance, reports, notifications. Mixed. media_reports is necessary if public galleries ship. Timestamps and soft deletes are necessary. friendships and notifications are premature if those screens remain placeholders. event_attendance is useful only if the app distinguishes RSVP intent from personal fridge layout. Add media_reports. Add timestamps and deleted_at. Add event_saves or event_attendance only when product behavior requires it. Defer friendships and notifications.
Reject Google hd may replace PFW verification. The Google hd claim itself is real and useful for Google Workspace domains. The weak part is the assumption that PFW students have Google-hosted pfw.edu accounts. PFW documentation points to Microsoft 365/Outlook for student email, matching the project's current understanding. Keep Google sign-in for easy account identity. Keep optional PFW verification as email OTP/magic-link to an @pfw.edu mailbox. Only use Google hd if a real PFW Google Workspace account can be confirmed.
Adopt Firebase-to-Supabase pivot should be documented. Correct. The repo still documents Firebase Auth as planned in CLAUDE.md and AGENTS.md. Silent architecture drift is exactly how future agents and developers make wrong assumptions. When the backend plan is accepted, update project docs with a concise decision record: Supabase chosen for Postgres, RLS, Auth, Storage, and smaller MVP operational surface.
Adopt Storage paths and bucket policy need definition. Correct. Supabase Storage access is policy-driven, and path conventions matter. This is cheap to decide now and messy to retrofit after uploads exist. Use explicit buckets and path conventions. Prefer private buckets with signed URLs for signed-in-only content. Public avatars are acceptable. Store metadata in Postgres.
Adopt Secret management is missing. Correct. Expo public env values are visible in the app bundle. Only Supabase URL and public anon key belong in the client. Put Anthropic keys, Supabase service-role key, and any privileged provider secrets in Edge Functions or another server-side environment.
Modify Cost and storage caps need quantification. Correct, but the proposed global cap needs adjustment. Supabase's free plan includes 1 GB file storage; a 15 GB global cap requires a paid plan. Videos can burn budget quickly. For free-tier development: images only, compressed, global storage alert at 750 MB, hard stop around 1 GB. If real beta galleries matter, plan for Supabase Pro before launch.
Adopt Fridge layout writes need debouncing. Correct. Customization is both a frontend and backend concern. Writing every small layout movement directly to Supabase will feel fragile on mobile networks. Store edits locally during gestures. Flush on debounce, screen exit, and app background. Use updated_at last-write-wins for the MVP.
Adopt Indexes should be part of Phase 0. Correct. Basic indexes are not overengineering; they make query intent explicit and prevent easy performance regressions. Add indexes for event ordering/search, fridge load by user, gallery by event/date, and report lookups. Use ILIKE search first; defer full-text/trigram until data volume justifies it.

Key Corrections to the Senior Review

PFW and Google Domain Verification

Google hd is valid for Google Workspace domains, but it is not a generic school-verification mechanism. Because PFW student email appears to use Microsoft 365/Outlook, this should not replace optional @pfw.edu email verification.

Storage Cap Math

Supabase's free plan includes 1 GB of file storage. A 15 GB global media cap is not free-tier compatible. If galleries are core to beta testing, assume Supabase Pro or strict image-only limits.

Social Tables

Adding a social graph too early increases RLS and product complexity. The backend should be ready to add friends later, but not carry unused tables unless the Friends screen becomes part of the active MVP.

AI Model Choice

A cheap, fast vision-capable model is plausible for flyer extraction, but the correct default should be chosen by testing against real flyers, not by architecture opinion alone.

Updated Decision Checklist Before Backend Work Starts

  1. Confirm Supabase as the official backend direction and document the Firebase-to-Supabase pivot.
  2. Create a dev Supabase project with real Auth users and RLS enabled from the first migration.
  3. Choose whether beta media is image-only. Recommendation: image-only until storage/moderation is proven.
  4. Define storage buckets and paths before implementing upload UI.
  5. Decide whether event_attendance is a real product concept or whether fridge_items is enough.
  6. Keep Google sign-in plus optional PFW email verification as the auth direction.
  7. Benchmark AI extraction later using real PFW flyer photos and manual correction data.
