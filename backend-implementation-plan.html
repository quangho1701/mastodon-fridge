Backend Implementation Plan

Phase-by-phase execution guide derived from final-decision.html. Each phase states the goal, the deliverables, an ordered task list, the files touched, the acceptance criteria, and known gotchas. The granular "how" — exact SQL, exact TypeScript — is left for build time, when you can use the model's thinking to generate it against the live codebase.

Stack: Expo + Supabase 7 phases • ~19 working days Solo developer Target: 50-user closed beta

How to use this document

Walk phases in order — each one assumes the previous is complete. When you reach a phase, paste its deliverables and the relevant existing screen/file paths into the model and let it generate the implementation. Do not pre-implement code in this document: it goes stale fast and steers the model away from current repo state.

Goal

One sentence — what this phase changes about the app.

Deliverables

Concrete artifacts (tables, screens, functions) that exist when the phase ends.

Order of operations

Numbered steps. Follow them top-to-bottom; each step is verifiable on its own.

Files touched

Existing files to wire up + new files to create. Use the repo path conventions in CLAUDE.md.

Done when

A small checklist that proves the phase actually works end-to-end.

Gotchas

Things that have eaten time on similar Supabase + Expo projects. Read these before starting.

Phases

0

Foundation

~2 days
Goal: The app boots against a real Supabase project as a real authenticated user, with RLS already on, indexes already in place, and an Edge Function already deployable. No features yet — just a verified rail.

Deliverables

  • Dev Supabase project with supabase/ directory committed.
  • One migration file containing the full Phase 0 schema, RLS policies, and indexes.
  • Two real Auth users seeded: dev1@local.test, dev2@local.test.
  • Supabase client + Auth context wired into App.tsx.
  • Dev auto-login working in Expo Go and web.
  • extract-flyer Edge Function deployed as a stub.

Files touched

  • New: supabase/migrations/0001_init.sql
  • New: supabase/functions/extract-flyer/index.ts
  • New: src/lib/supabase.ts
  • New: src/lib/auth.ts
  • New: src/contexts/AuthContext.tsx
  • Edit: App.tsx (wrap with AuthProvider)
  • New: .env.local (gitignored)
  • Edit: .gitignore

Order of operations

  1. Create the Supabase dev project; copy URL and anon key into .env.local.
  2. Run supabase init in the repo root; commit the generated supabase/ tree (minus .branches/).
  3. Link the local project to the dev cloud project: supabase link --project-ref <ref>.
  4. Write 0001_init.sql: create all six MVP tables (profiles, events, fridge_items, gallery_media, media_stickers, media_reports), enable RLS on each, write the initial policies (see "RLS starting policies" reference below), create indexes.
  5. Apply: supabase db push. Verify the schema in the dashboard.
  6. Create dev users via the dashboard Auth UI (or a separate seed.sql). Insert matching profiles rows for each.
  7. Install npm deps; create src/lib/supabase.ts with the client (use AsyncStorage as the auth storage adapter, import the URL polyfill at the top of the file).
  8. Create AuthContext: exposes { user, session, signIn, signOut }. On mount, if __DEV__ and the dev env vars are present, auto-call signInWithPassword.
  9. Wrap App.tsx in AuthProvider inside ThemeProvider.
  10. Add a temporary debug surface (e.g. log session?.user.id in FridgeScreen) to confirm sign-in works on Expo Go and web.
  11. Scaffold extract-flyer Edge Function returning a hard-coded JSON shape; deploy with supabase functions deploy extract-flyer; set ANTHROPIC_API_KEY via supabase secrets set.
  12. Cross-user isolation test: using SQL editor, sign in as dev1 via auth.uid() simulation and confirm SELECT against another user's fridge_items returns zero rows.

Done when

  • Cold launching Expo Go shows the user logged in within ~1 second; session.user.id is real.
  • supabase db push applies the migration cleanly to a fresh project (verify by resetting the dev DB).
  • Calling the deployed Edge Function from curl with a user JWT returns the stub JSON.
  • RLS isolation test: dev2 cannot read dev1's rows in any table that has owner-only RLS.

Gotchas

  • Supabase JS on RN requires react-native-url-polyfill/auto imported before the client. Forgetting this surfaces as cryptic URL is not defined errors.
  • The profiles row for an Auth user is not created automatically. Either insert it manually for dev users, or write a Postgres trigger on auth.users insert. The trigger is a one-liner; do it in the same migration.
  • Don't enable Supabase email confirmation on dev — it blocks the seeded password sign-in.
  • RLS "permissive enough for testing" still means owner-only on fridge_items from day one; this is the table that proves your isolation actually works.

Events & Market

~3 days
Goal: Real users can create, list, search, and view events. MarketScreen renders from Postgres, not seeds.

Deliverables

  • src/lib/api/events.ts with listEvents, getEvent, createEvent, updateEvent, deleteEvent.
  • MarketScreen wired to listEvents with pull-to-refresh and basic search.
  • An event detail screen or modal (decide based on existing nav).
  • ConfirmScreen save path calls createEvent.

Files touched

  • New: src/lib/api/events.ts
  • Edit: src/screens/MarketScreen.tsx
  • Edit: src/screens/ConfirmScreen.tsx
  • New (maybe): src/screens/EventDetailScreen.tsx + route in RootNavigator

Order of operations

  1. Implement events.ts CRUD wrappers around the Supabase client. Return typed rows; use a generated Database type from supabase gen types typescript.
  2. Replace the mock event list in MarketScreen with a useEffect + state pattern (no server-state library yet; keep it simple).
  3. Add pull-to-refresh and a debounced search input that re-runs listEvents({ search }); in the API, build an .or() clause with title.ilike and description.ilike.
  4. Wire ConfirmScreen's save button to createEvent using its existing extractedTitle / extractedStartDate / extractedEndDate / extractedLocation params, plus the captured flyer image path (uploaded in Phase 3 — for now, save without flyer image).
  5. Add an event detail view (modal or pushed screen) that pulls getEvent(id). Reuse it from MarketScreen taps and from fridge items in Phase 2.
  6. Add RLS write tests: signed in as dev2, attempting to update an event created by dev1 must fail.

Done when

  • Creating an event in ConfirmScreen persists it; closing the app and reopening shows the same event in Market.
  • Searching "yoga" filters the list to events with "yoga" in title or description.
  • Two devices logged in as different users see the same events.
  • dev2 cannot edit or delete dev1's event.

Gotchas

  • Supabase returns created_at as ISO strings, not Date. Decide whether your TS types use string (simpler) or Date (parse at the API boundary).
  • Don't reach for React Query / SWR yet; the screens are simple enough that useEffect + useState is shorter and avoids a dependency.

Fridge customization

~2 days
Goal: Each user's personal fridge persists. Drag, rotate, and re-pin survive an app relaunch on the same account, and another user logging in sees their own (empty) fridge.

Deliverables

  • src/lib/api/fridge.ts with listFridgeItems, upsertFridgeItem, removeFridgeItem, flushFridgeItems(items[]).
  • FridgeScreen reads from Postgres on mount, holds layout state in memory + AsyncStorage, flushes to Supabase on a 1.5s debounce + on screen blur + on app background.
  • "Pin to fridge" action from event detail creates a fridge_items row with event_id.

Files touched

  • New: src/lib/api/fridge.ts
  • Edit: src/screens/FridgeScreen.tsx
  • Edit: src/data/fridgeSeed.ts (likely deprecated for live data; keep the type definitions, mark seed as legacy)
  • Edit: Whichever component currently dispatches the pin action.

Order of operations

  1. Implement fridge.ts with a flushFridgeItems that takes a batch and uses upsert on id.
  2. On FridgeScreen mount: listFridgeItems() filtered by the current user; merge with whatever is in AsyncStorage under a per-user key (local wins for unsynced edits).
  3. Build a useFridgeStore hook (just useReducer) that holds the current items, exposes moveItem, rotateItem, removeItem, addItem; every mutation also writes to AsyncStorage.
  4. Add a debounce: 1.5s after the last mutation, call flushFridgeItems; also flush on screen blur (useFocusEffect cleanup) and on AppState change to background.
  5. Hook gestures via built-in PanResponder. Keep math simple: store position as raw x, y; ignore screen-size normalization for MVP — the fridge frame is a fixed-size container.
  6. Add an "unpin" affordance (long-press or button) that calls removeFridgeItem with optimistic local removal.
  7. Verify across two devices: pinning on device A under dev1 appears on a fresh launch on device B under dev1; dev2 sees nothing.

Done when

  • Drag-drop a magnet, kill the app, reopen — it stays put.
  • Toggling between dev1 and dev2 swaps the fridge contents.
  • Network flakiness during dragging does not lose edits (kill wifi, drag, restore wifi → eventual flush succeeds).
  • dev2 cannot read or modify dev1's fridge_items via direct Supabase client calls.

Gotchas

  • Without react-native-reanimated, every frame is a JS-thread re-render. Throttle the onPanResponderMove setState to ~30fps to avoid jank on Android.
  • Per-user AsyncStorage key (e.g. fridge:items:<userId>) is mandatory — otherwise switching users on the same device leaks state.
  • Server-side conflict resolution is "last write wins" by row id. With one device per user this won't surface; don't build a CRDT.

Storage + media safety skeleton

~2 days
Goal: The app can upload a compressed image and read it back via a signed URL. The security primitive ("only authenticated users can read non-removed gallery media") is enforced server-side, not by the client.

Deliverables

  • Three private buckets created: flyers, gallery, avatars.
  • Storage RLS policies on each bucket, scoped by {user_id}/ path prefix.
  • A Postgres function get_signed_media_url(media_id uuid) that returns a short-lived signed URL after auth + moderation checks, callable as an RPC.
  • src/lib/storage.ts with uploadImage(bucket, file) that compresses then uploads.

Files touched

  • New: supabase/migrations/0002_storage.sql
  • New: src/lib/storage.ts
  • Edit: Avatar upload in ProfileScreen (smallest scope to validate end-to-end).

Order of operations

  1. Migration 0002_storage.sql: create the three buckets via storage.create_bucket; write storage policies that allow inserts only when the path starts with auth.uid()::text || '/'.
  2. Implement get_signed_media_url: a SQL/PLpgSQL function that takes a media_id, looks up gallery_media, ensures moderation_status <> 'removed' and deleted_at IS NULL, then calls storage.create_signed_url with a 60-minute expiry. Mark SECURITY DEFINER so it can read storage internals.
  3. Implement uploadImage: take the raw URI, run expo-image-manipulator (resize to 1600px longest edge, JPEG quality 0.7), reject anything still over 5 MB, then supabase.storage.from(bucket).upload(path, blob). Path follows {user_id}/{uuidv4}.jpg.
  4. Validate the entire round-trip via avatar: ProfileScreen upload → save the path on profiles.avatar_path → render via a signed URL (avatars can use a long-expiry signed URL fetched on profile load).
  5. Confirm dev2 cannot upload to a path under dev1's prefix (storage policy denies).

Done when

  • Picking an avatar in ProfileScreen uploads <1 MB regardless of original size, persists across launches, and renders.
  • Direct unauthenticated access to the storage object URL (no signed token) returns 403.
  • get_signed_media_url for a removed row returns null/error — proving the moderation gate works at the server level.

Gotchas

  • Supabase Storage on RN has had repeated bugs around upload payloads; if a direct upload call fails on Android specifically, fall back to uploadFromBase64 via FileSystem.readAsStringAsync.
  • Signed URLs are cacheable; if you re-render frequently, memoize the URL per media_id for its expiry duration to avoid burning RPC calls.
  • Bucket names are global to the project — pick them once, never rename.

Public galleries with reports

~3 days
Goal: Any signed-in user can upload photos to an event gallery, view others' photos, place sticker overlays, and report content. An admin can remove reported content with a single update.

Deliverables

  • src/lib/api/gallery.ts: listGalleryMedia, uploadGalleryMedia, placeSticker, reportMedia.
  • EventGalleryScreen wired to real data, including sticker overlays (read from media_stickers).
  • A simple admin utility — either a hidden "Admin" section in ProfileScreen shown only when profiles.is_admin = true, or just SQL snippets in a markdown file. The first is barely more work; do it.

Files touched

  • New: src/lib/api/gallery.ts
  • New: src/lib/api/reports.ts
  • Edit: src/screens/EventGalleryScreen.tsx
  • Edit: src/screens/ProfileScreen.tsx (admin section)
  • New (maybe): src/screens/admin/ReportsQueueScreen.tsx

Order of operations

  1. Wire EventGalleryScreen to listGalleryMedia(eventId); render via signed URLs from get_signed_media_url. Pull-to-refresh, no realtime.
  2. Add upload entry point. Use the existing expo-image-picker already in the package list. Reject videos client-side (mediaTypes: Images). Insert a gallery_media row with moderation_status = 'approved'.
  3. Sticker placement: tap a sticker affordance, tap a position on the image; insert into media_stickers with x_percent/y_percent. Re-fetch overlays for the affected media.
  4. Report flow: long-press on a photo → "Report" → reason picker (4 fixed options) → insert into media_reports. Show a one-time toast.
  5. Admin queue: list media_reports joined to gallery_media; one button per row, "Remove": sets moderation_status = 'removed', reviewed_by = auth.uid(), reviewed_at = now(). Auto-soft-deletes via deleted_at = now() on the same row.
  6. Verify a removed photo no longer returns from get_signed_media_url; existing client cache should fail to fetch and the image goes blank or shows a placeholder.

Done when

  • Two users on two devices see each other's uploaded photos in the same event gallery.
  • Reports written by dev2 show up in the admin queue when logged in as an admin.
  • "Remove" hides the photo from everyone's gallery within one refresh.
  • Stickers placed on a photo persist and render in the same relative positions across devices.

Gotchas

  • The "approved by default" closed-beta default is set in the migration as a column default — don't reimplement it in app code.
  • If you use FlatList for the gallery, the signed URL needs to be stable across renders; otherwise images flicker on every state update.
  • Large photos uploaded over slow networks can time out. Set a reasonable uploadTimeout and surface failures to the user; don't silently retry.

AI flyer extraction

~3 days
Goal: A user scans a flyer; the Edge Function returns structured event fields; the ConfirmScreen fills in but always allows manual correction.

Deliverables

  • Real extract-flyer Edge Function that calls Claude Haiku 4.5 with the image and a strict JSON-output prompt.
  • Server-side rate limit: 20 extractions per user per day, enforced via an ai_extractions log table.
  • src/lib/api/ai.ts wrapping the function call.
  • ScanScreen calls the function with the captured image; ConfirmScreen consumes the response.

Files touched

  • Edit: supabase/functions/extract-flyer/index.ts
  • New: supabase/migrations/0003_ai_extractions.sql
  • New: src/lib/api/ai.ts
  • Edit: src/screens/ScanScreen.tsx
  • Edit: src/screens/ConfirmScreen.tsx (handle low-confidence fields)

Order of operations

  1. Migration 0003_ai_extractions.sql: ai_extractions(id, user_id, created_at, model, success) with an index on (user_id, created_at) for the rate-limit count.
  2. Edge Function: receive base64 image (or signed URL), check today's count for the user — fail with 429 if >= 20. Call anthropic.messages.create with claude-haiku-4-5-20251001, vision input, and a system prompt that demands strict JSON: { title, description, starts_at, ends_at, location, confidence: { ... per field } }.
  3. Validate the response shape with a small JSON-schema validator (or hand-rolled checks). Insert an ai_extractions row regardless of outcome (so failures still count toward the daily limit, preventing abuse via failed calls).
  4. ScanScreen: after capture and compression, upload the image to flyers/{user_id}/{uuid}.jpg, then call the Edge Function with the storage path; the function fetches the image via signed URL.
  5. ConfirmScreen: render fields with low confidence as visually distinct (subtle warning style) and pre-focused for editing.
  6. Test against 20–30 real PFW flyers (the user can take photos around campus). Track field accuracy. If it's below ~85%, swap model to claude-sonnet-4-6 in the function — no client changes needed.

Done when

  • End-to-end scan returns structured fields in < 6 seconds on a normal mobile network.
  • Hitting the rate limit (21st call in a day) returns a clear "you've reached today's limit" error in the UI.
  • The function never crashes on malformed model output; it returns a graceful fallback ({ confidence.all: 0 }) so the user can fill the form by hand.
  • Anthropic key is reachable only from the function — the Expo bundle is searched and contains no sk-ant- string.

Gotchas

  • Don't pass the raw image bytes through the Expo bundle to the function as base64; it bloats the payload. Upload to storage first, send the path, let the function fetch.
  • Edge Functions cold-start on Deno (~300ms after idle). Keep one keep-warm cron only if latency complaints surface in user testing — otherwise live with it.
  • Claude vision can hallucinate dates that "sound campus-y" (next Friday, etc.). The system prompt should explicitly say "if a field is not visible in the image, set its confidence to 0 and the value to null." Verify this with adversarial flyers.

Production auth + prod project

~3 days
Goal: Ship a production Supabase project with Google sign-in. Optional @pfw.edu magic-link verification stores a badge on the profile but never gates writes.

Deliverables

  • New mastodon-fridge-prod Supabase project with all migrations applied.
  • Google OAuth provider configured in Supabase Auth.
  • EntryScreen ("Sign in with Google") working in dev builds against prod project.
  • Optional PFW magic-link flow (Edge Function + transactional email provider).
  • Per-build env switching (dev project for development, prod project for prod builds).

Files touched

  • Edit: src/lib/auth.ts — add real Google sign-in path; gate dev auto-login on __DEV__ && isDevProject.
  • Edit: src/screens/EntryScreen.tsx — replace placeholder buttons.
  • Edit: src/screens/ProfileScreen.tsx — "Verify PFW" affordance.
  • New: supabase/functions/send-pfw-otp/index.ts
  • New: supabase/functions/verify-pfw-otp/index.ts (or one combined function)

Order of operations

  1. Create the prod Supabase project. Apply all migrations (supabase db push --project-ref <prod>).
  2. Set up a Google Cloud OAuth client (Web + iOS + Android). Add the redirect URLs Supabase requires. Configure the Google provider in Supabase Auth.
  3. In auth.ts, implement signInWithGoogle using supabase.auth.signInWithOAuth({ provider: 'google' }); on web it redirects, on native it uses WebBrowser.openAuthSessionAsync via expo-auth-session if needed.
  4. Add a handle_new_user trigger (or update the existing one) that auto-creates a profiles row whenever a new auth.users row is inserted.
  5. Pick a transactional email provider — recommend Resend (cleaner API for one-off email). Get an API key, set it via supabase secrets set.
  6. Implement the PFW OTP flow. Two options that both work:
    • (A) Custom token: send-pfw-otp emails a 6-digit code, stored hashed in a pfw_otp(profile_id, code_hash, expires_at) table. verify-pfw-otp compares.
    • (B) Magic link: send-pfw-otp generates a signed token (JWT-ish) and emails a deep link; tapping it hits a verify endpoint that updates pfw_verified_at.
    Either is fine; (A) is slightly simpler for mobile-only entry.
  7. The verify endpoint must enforce the email is on the pfw.edu domain. Reject anything else with a clear error.
  8. Ship the "Verify PFW" affordance in ProfileScreen with a "Verified PFW Don" badge once pfw_verified_at is set.
  9. Run the entire dev → prod flow in a clean install: install the app, sign in with a real Google account, optionally verify PFW email, create an event, upload a photo. End-to-end on prod data.

Done when

  • Cold install + Google sign-in + first event creation works on iOS Simulator, Android Emulator, and web.
  • The user record exists in auth.users and the matching profiles row exists with correct defaults.
  • Verifying with a real @pfw.edu email sets pfw_verified_at and shows the badge.
  • Trying to verify with a non-PFW email fails with a clear message.
  • Dev auto-login is impossible in production builds (dev env vars are not bundled).

Gotchas

  • Native OAuth redirect URIs are the most common production-blocking bug. Test on a real device before declaring this phase done — simulators sometimes succeed where physical phones fail.
  • Supabase's OAuth flow on iOS requires you to register a custom URL scheme in app.json. Add it before testing.
  • Google's account picker on Expo Web sometimes opens in a popup blocked by browser settings; document the workaround in the README.
  • If using Resend, configure SPF/DKIM on the sending domain or all OTP emails go to spam. Free Resend has a sandbox mode that avoids this for early testing — use it.

  • Edit: CLAUDE.md
  • Edit: AGENTS.md (if exists)
  • New: docs/admin-runbook.md
  • New: docs/backups.md

  1. Write rls-audit.ts: it signs in as dev2, then attempts ~12 operations (read/update/delete on each user-owned table targeting dev1's rows). Asserts every one fails with a permission error. Run it as part of "is the dev project still safe" checks.

  3. Update CLAUDE.md: tech stack changes from "Firebase Auth (planned), Claude Vision API (planned for backend)" to "Supabase (Postgres, Auth, Storage, Edge Functions); Anthropic Claude Haiku 4.5 via Edge Function for flyer extraction." Add the dev-auth section.

Reference — RLS starting policies

The actual SQL is for the model to generate at Phase 0 build time, but here's the policy intent table to check generated SQL against:

Table SELECT INSERT UPDATE DELETE
profiles any authenticated user (limited columns) via trigger only self only none (account deletion is admin-only)
events any authenticated, deleted_at IS NULL created_by = auth.uid() created_by = auth.uid() created_by = auth.uid() (sets deleted_at)
fridge_items user_id = auth.uid() user_id = auth.uid() user_id = auth.uid() user_id = auth.uid()
gallery_media auth + moderation_status <> 'removed' + deleted_at IS NULL uploaded_by = auth.uid() self (own row) OR is_admin self (own row) OR is_admin
media_stickers any authenticated placed_by = auth.uid() placed_by = auth.uid() placed_by = auth.uid()
media_reports is_admin only reporter_id = auth.uid() is_admin only none
ai_extractions user_id = auth.uid() via Edge Function (service role) none none

Reference — daily working loop

For each phase, the practical loop looks like this:

  1. Open this document. Read the phase's Goal and Order of operations.
  2. Open the model with: the phase's deliverables, the listed files, and the relevant existing screens. Ask it to implement the next 1–2 steps.
  3. Run npm run lint after every step that touches TypeScript.
  4. For Supabase changes: write the SQL into a numbered migration file in supabase/migrations/; apply with supabase db push; never edit the dev database directly via the dashboard for schema changes.
  5. For Edge Function changes: supabase functions deploy <name>, then call from the app or curl with a real user JWT.
  6. At the end of the phase, run the Done when checklist by hand. Don't move on until every box is real.
One rule: Don't go back to a previous phase to "improve" it once you've left. Note the improvement in a BACKLOG.md and revisit after the ship gate. The MVP isn't done until all seven phases are done; partial perfection on Phase 2 doesn't count.

What you do not need to plan now

These are the things that look like they need planning but are better answered by the model at build time with the live codebase in hand:

  • Exact SQL for migrations (Phase 0, 2, 3, 5).
  • Exact TypeScript shape of the API wrappers — generate from supabase gen types typescript.
  • Exact gesture math for fridge dragging (Phase 2). Standard PanResponder recipe.
  • Exact Anthropic prompt for flyer extraction (Phase 5). Iterate against real flyers.
  • Exact Resend email template (Phase 6). Plain text is fine.
  • Exact admin UI — a FlatList + one button is enough.

If you find yourself writing more planning instead of building, that is the signal to stop and start Phase 0.
